Source: jadx decompile of Sony Sound Connect 13.2.2 (paths below are relative to the jadx `sources/` root; `v2/` = `com/sony/songpal/tandemfamily/message/mdr/v2/`). Read-only research; no device was touched. Anything not directly verified in code is marked **UNCONFIRMED**.

## 1. Resolving jadx constant substitutions

jadx replaces small integer literals with any same-valued `static final` constant it knows (from `org.bson.BSON` and `org.opencv.imgproc.Imgproc`, which are bundled libraries). They are purely cosmetic: read the constant's definition and substitute the literal. In `FunctionType.java` the `BSON.*` substitutions occur in the **byte-code** slot (3 entries) and all `Imgproc.*` substitutions occur only in the **ordinal** slot (they do not affect byte codes). Other files (Command.java, `*InquiredType.java`, `DataType.java`, `table1/c.java` case labels) use the same trick.

## 2. How a FunctionType maps to messages

- `FunctionType(name, ordinal, Table, byteCode)` — `v2/FunctionType.java:133-422`. `fromByteCode(Table, byte)` (`v2/FunctionType.java:432`) matches both table and byte, so table-1 and table-2 codes overlap (e.g. 0x20 is BATTERY_LEVEL_INDICATOR in table 1 and AUTO_STANDBY in table 2).
- Frame type: table 1 = `DataType.DATA_MDR` = **0x0c** (`com/sony/songpal/tandemfamily/message/DataType.java:13`, `v2/table1/c.java:1004`); table 2 = `DataType.DATA_MDR_NO2` = **0x0e** (`DataType.java:15`, `v2/table2/c.java:586`).
- The **high nibble of the function code selects the command family** (observed convention, holds for every mapped entry): table 1 `0x1_` COMMON (0x10-0x19), `0x2_` POWER (0x20-0x29), `0x3_` UPDT (0x30-0x3f), `0x4_` LEA (0x40-0x4d), `0x5_` EQEBB (0x50-0x5b), `0x6_` NCASM (0x60-0x69), `0x7_` SENSE (0x70-0x7b), `0x8_` OPT (0x80-0x89), `0x9_` ALERT (0x90-0x99), `0xa_` PLAY (0xa0-0xa9), `0xb_` SAR_AUTO_PLAY (0xb0-0xb9), `0xc_` LOG (0xc4, 0xc9), `0xd_` GENERAL_SETTING (0xd0-0xd9), `0xe_` AUDIO (0xe0-0xe9), `0xf_` SYSTEM (0xf0-0xfd) — opcodes in `v2/table1/Command.java:9-160`. Table 2: `0x2_` POWER (0x20-0x29), `0x3_` PERI (0x30-0x3d), `0x4_` VOICE_GUIDANCE (0x40-0x4b), `0x5_` SAFE_LISTENING (0x50-0x5b), `0x6_` LEA (0x60-0x69), `0x7_` PARTY (0x70-0x7c), `0xf_` SYSTEM (0xf0-0xfd) — `v2/table2/Command.java:8-90`. Both tables share CONNECT 0x06/0x07.
- Inside a family, payload byte 1 is the family's **InquiredType** (e.g. `NcAsmInquiredType`), which is *not* the function code (exception: `GsInquiredType` bytes equal the function codes 0xd1-0xd4). The FunctionType→InquiredType mapping below is by name and is confirmed where the app's init sequence issues `contains(FunctionType.X) → getCapability(XInquiredType.Y)` in `wv/e.java` (cited as "init").
- Message classes are obfuscated. Parser factory: `v2/table1/c.java:670-968` / `v2/table2/c.java:388-550` map each Command to a class; obfuscated package per family — table 1: connect `ff0`, common `ef0`, power `vf0`, updt `eg0`, lea `kf0`, eqebb `gf0`, ncasm `pf0` (+ payload helpers `rf0`), sense `xf0`, opt `sf0`, alert `bf0`, play `tf0`, sarautoplay `wf0`, log `nf0`, generalsetting `if0`, audio `cf0`, system `ag0`; table 2: connect `gg0`, power `ng0`, peripheral `lg0`, voiceguidance `xg0`, safelistening `og0`/`rg0`/`qg0`/`pg0`, lea `hg0`, party `jg0`, system `tg0`.
- The "Opcodes" column lists every Command whose message class references that InquiredType constant, with one `file:line` citation (the class that holds the `Command.X` constant). `GET_*` requests are often generic builders taking the InquiredType as an argument, so a missing `GET_x` usually still exists as opcode `RET_x − 1` of the same family.
- Dispatch quirk: POWER RET/NTFY classes route inquired byte 14 (`STAMINA`) to a raw passthrough (`v2/table1/c.java:706-722`, `Collections.singleton(14)`); SYSTEM GET/RET/SET/NTFY_STATUS, RET_PARAM, NTFY_PARAM route inquired bytes {1, 11} to raw `v2/table1/d.java` (`v2/table1/b.java` set `{1, 11}`, `v2/table1/c.java:946-960`).

## 3. XM6 support-function payload and parser check

Live XM6 table-1 `CONNECT_RET_SUPPORT_FUNCTION`: `07 00 31 …` = 101 bytes = 3 + 2·0x31 → 49 entries. Pairing confirmed as `(functionType, capabilityCounter)`: parser `ff0/l.java:26` checks `len == bArr[2]*2 + 3`, and `ff0/l.java:62-64` reads `FunctionType.fromByteCode(Table.NO_1, b[3+2i])` then counter `b[4+2i]`. Unknown codes are dropped (`NO_USE`). All 49 XM6 codes resolve to a known table-1 FunctionType. `0x34` is FW_UPDATE_MTK_TRANSFER_WITHOUT_DISCONNECTION_AUTO_UPDATE with counter 0x41. A counter of 0xff appears to be the "no version" value (UNCONFIRMED semantics).

## 6. Table-2 support-function request

Table 2 has its own `CONNECT_GET_SUPPORT_FUNCTION` (`v2/table2/Command.java:8`, opcode 0x06) built by `gg0/a.java:35-39`: payload **`06 00`** (`Command.CONNECT_GET_SUPPORT_FUNCTION`, `ConnectInquiredType.FIXED_VALUE`=0x00 from `v2/table2/connect/param/ConnectInquiredType.java:6`), sent on frame type **0x0e** (`DataType.DATA_MDR_NO2`, `v2/table2/c.java:586`; the app's `SonyFrame.TYPE_COMMAND2 = 0x0e`). So the only difference from the table-1 request (`06 00` on frame 0x0c, `ff0/d.java:34-38`) is the frame type.

Reply: `CONNECT_RET_SUPPORT_FUNCTION` `07 00 <count> {functionType, counter}*count` on 0x0e, parsed with `Table.NO_2` (`gg0/b.java:44`, `:80-86`). Note `gg0/b.java:30-39,53-54`: the app rejects a table-2 reply that contains **both** SAFE_VOLUME_CONTROL (0x54) and MAX_VOLUME_LEVEL_LIMIT (0x55).
